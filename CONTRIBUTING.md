# Contributing to Lore

Thanks for your interest in improving Lore! This project uses the standard
**fork‑and‑pull‑request** workflow. You don’t have push access to this
repository — instead you fork it, push to your fork, and open a pull request.
The maintainer reviews and merges.

## Workflow

1. **Fork** the repo on GitHub (`crswebb/Lore`).
2. **Clone** your fork and create a topic branch:
   ```bash
   git clone https://github.com/<you>/Lore.git
   cd Lore
   git checkout -b my-change
   ```
3. Make your change, keeping commits focused and the build green.
4. **Push** to your fork and **open a PR** against `crswebb/Lore`’s `main`.
5. Respond to review feedback; the maintainer merges once it’s ready.

For anything large or architectural, please **open an issue first** to discuss
the approach before investing a lot of time.

## Prerequisites

- **macOS 26 (Tahoe)** or later.
- **Xcode 26**.
- **XcodeGen** — `brew install xcodegen`.
- **Ollama** *(optional)* — only if you’re working on the Ollama provider or want
  local‑model chat while testing. See <https://ollama.com>.

## Building & running

```bash
./run.sh          # regenerate project, build, and launch
```

Or, for the Swift packages on their own (faster for logic work, no Xcode UI):

```bash
cd LorePackages
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift build --target LoreRAG
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test
```

> The package declares `platform: .macOS(.v26)`, so a build needs the macOS 26
> SDK from Xcode 26. Set `DEVELOPER_DIR` (as above) if `xcode-select` points at
> the Command Line Tools rather than Xcode.

## Project conventions

- **`project.yml` is the source of truth.** `Lore.xcodeproj` is generated by
  XcodeGen and is git‑ignored. Never commit `Lore.xcodeproj/` or `build/`. If you
  change targets, settings, or files, edit `project.yml` and re‑run
  `xcodegen generate`.
- **Swift 6, strict concurrency.** `async`/`await` throughout; keep types
  `Sendable` where they cross actors.
- **Modular boundaries.** UI never touches SQL directly — go through a repository
  in `LorePersistence`. New model back‑ends implement `LLMProvider` /
  `EmbeddingProvider` in `LoreProviders`; feature code stays provider‑agnostic.
- **Match the surrounding style** — naming, comment density, and idioms of the
  file you’re editing. Comments explain *why*, not *what*.
- **Privacy is a feature.** Don’t add network calls, analytics, or telemetry.
  Any new egress must be user‑initiated and visible.

## Adding or changing UI strings (localization)

The UI is localized into English, German, Spanish, French, and Swedish. When you
add or change user‑facing text:

1. Wrap it in the `L(...)` helper — e.g. `Text(L("New Shelf"))`. The English
   source text **is** the key. Use `%@` / `%d` (and positional `%1$@`, `%2$@`
   where word order differs across languages) for interpolation.
2. Add the same key to **all five** files in `App/*.lproj/Localizable.strings`.
   Keep the key sets identical across languages. A missing translation falls back
   to the English key, so English must always be present.
3. A change with no translation is fine to submit — flag it in the PR and a
   maintainer or another contributor can supply the other languages.

Test a language with:
```bash
defaults write se.crswebb.Lore AppleLanguages -array de   # or es / fr / sv / en
```
and reset with `defaults delete se.crswebb.Lore AppleLanguages`. (You can also
switch it live in **Settings › Appearance › Language**.)

## Commit & PR guidelines

- Write commit messages in the imperative mood, with a short subject line and a
  body explaining the *why* when it isn’t obvious.
- Keep a PR to one logical change. Note anything you couldn’t test.
- Make sure `swift build` and `swift test` pass, and the app launches.
